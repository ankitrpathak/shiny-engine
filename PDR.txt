ON DEMAND CAR WASH PLATFORM
PROJECT DESIGN REPORT (PDR)

Prepared for AI-driven project generation and full-stack implementation
Date: 10 Oct 2026


1. PROJECT OVERVIEW
The On Demand Car Wash platform is a production-ready, role-based, microservice-based web application for booking vehicle cleaning and detailing services online. The system connects customers, washers, and administrators in one ecosystem where customers can browse service packages, book appointments, make payments, leave reviews, and receive notifications; washers can manage assigned jobs and view schedules; and administrators can manage users, approve or block accounts, assign washers, monitor payments, and track operational metrics.

This solution follows a real-world architecture that separates concerns across multiple Spring Boot microservices and a modular Angular frontend. It uses RESTful APIs, JWT-based security, role-based authorizations, RabbitMQ for asynchronous messaging, and Razorpay for payment integration. The application is designed to be scalable, modular, and secure, while remaining easy to extend for production deployment.

The project being rebuilt in this repository already contains a major architectural backbone:
- API Gateway
- Eureka Discovery Server
- User Service
- Admin Service
- Booking Service
- Payment Service
- Review Service
- Notification Service
- Angular Frontend

The architecture supports role-based flows such as:
- Customer logs in and creates profile
- Admin promotes user to washer/admin
- God super admin can promote or demote user roles
- Users can update their profile
- Admin can block/activate users
- Washer can see his own profile and assignments
- Customer can view his own bookings, reviews, payments, notifications
- Admin gets dashboards and summaries


2. BUSINESS OBJECTIVE
The core objective is to create a reliable digital platform that allows customers to request car wash services quickly and conveniently while helping business owners manage operations efficiently. The system must avoid business logic flaws, support secure access control, and provide a clean, responsive dashboard for all roles.

Primary goals:
- Allow customers to register, login, and manage profile
- Enable service package browsing and booking
- Assign washers to bookings
- Track job status from creation to completion
- Accept online payments using Razorpay test mode
- Send notifications asynchronously through RabbitMQ
- Collect customer feedback and reviews
- Maintain system health, analytics, and summaries for admin
- Protect data and routes with JWT + Spring Security
- Make data and workflows accessible via REST API and Angular UI


3. TARGET USERS AND ROLES
The platform supports 4 major roles and access levels:

3.1 CUSTOMER / NORMAL USER
Customer is the default role after profile creation. He can:
- Register and login
- Update personal profile
- View his profile and account status
- Browse service packages and create bookings
- View assigned job status and booking history
- Make payment against bookings
- View payment status and transaction history
- Add reviews for completed bookings and washers
- Receive notifications
- Request services and manage his own bookings

3.2 WASHER
Washer is promoted by Admin or God Super Admin. Washer can:
- Login with washer role
- See his own profile
- View assigned bookings
- Update booking status (in progress/completed etc.)
- Track personal workload and history
- View ratings/reviews received
- Access only needed tasks

3.3 ADMIN
Admin has operational control over the system. Admin can:
- View all users
- Block or activate users
- Promote users to admin or washer
- View dashboard summaries
- Manage service packages
- Monitor bookings, payments, reviews, notifications
- Assign washers to bookings
- Manage system configuration and reports

3.4 GOD SUPER ADMIN
This is the master root account, named "God". It is a protected, non-alterable super-admin identity. It can:
- Promote a user to admin or washer
- Demote a user back to customer
- Keep the platform operationally secure
- Block or activate user accounts with high authority
- Manage platform-level governance without being editable by others
- Ensure no other user, even admin, can modify or remove this account

Important rule: the God super admin is immutable and protected from tampering, alteration, or role removal.

- Controller Layer: exposes REST endpoints
- Service Layer: contains business logic and validations
- Repository Layer: handles persistence
- Entity Layer: database models
- DTO Layer: request/response objects
- Security Layer: JWT filter, config, method security
- Exception Layer: handles validation and domain errors
- Asynchronous Messaging: RabbitMQ producer/consumer integration when needed

5.2 MAIN COMPONENTS
- Frontend: Angular application in Frontend/odc-frontend

- SonarQube: code quality and static analysis

5.3 TECHNOLOGY STACK

7. SECURITY DESIGN
Security is a core design requirement and is already embedded in the backend architecture.

7.1 JWT SECURITY MODEL
The system uses JWT for stateless authentication and authorization.

JWT responsibilities:
- User logs in with email/password
- Server validates credentials
- JWT is issued with user identity and role
- Token is included in Authorization headers for protected endpoints
- Filter validates token and extracts principal/role
- Role-based access checks are done using @PreAuthorize

Protected roles from code examples:
- ADMIN can access admin actions and summaries
- WASHER can access personal profile, assignments, and role-specific endpoints
- CUSTOMER can access self-service booking and profile flows

7.2 SPRING SECURITY CONFIGURATION
Each microservice includes a security configuration with:
- SecurityFilterChain
- JwtAuthenticationFilter
- @EnableMethodSecurity
- Protected routes and excluded Swagger docs
- JWT validation on incoming requests
- Extraction of email and role from token

7.3 ROLE VALIDATION RULES
- Authenticated user must have required role to access endpoint
- Example: blockUser requires ADMIN
- Example: getBookingSummary requires ADMIN
- Example: updateBookingStatus allowed for ADMIN and WASHER
- Example: getMyAssignments requires WASHER

7.4 GOD SUPER ADMIN RULE
The system must define a protected account called "God" as a root super admin that cannot be edited, blocked, or demoted by any normal admin or user. This is a critical governance requirement.

Implementation constraints:
- User service should enforce immutability of the God account in promotion/demotion workflows
- Admin endpoints must reject attempts to promote or demote God
- Admin operations should be validated before they mutate the user entity


8. HTTP METHODS AND RESTFUL API DESIGN
The backend uses standard REST semantics. The project should follow the following patterns consistently:

- GET: fetch a resource or list
- POST: create a new resource or action
- PUT: modify existing resource or state
- DELETE: remove a resource where allowed

Examples from the project:
- Register user: POST /api/auth/register
- Login user: POST /api/auth/login
- Create booking: POST /api/bookings
- Update booking status: PUT /api/bookings/{bookingId}/status/{status}
- Assign washer: PUT /api/bookings/{bookingId}/assign/{washerId}
- Admin block user: PUT /api/admin/users/{userId}/block
- Update user: PUT /api/users/{id}
- Delete user: DELETE /api/users/{id}
- Promote user as admin: PUT /api/users/{id}/promote-admin

This is aligned with the requirement to Handle different HTTP methods (GET, POST, PUT, DELETE).

- Payment service publishes notification on payment status

11.2 CONFIGURATION
The project includes RabbitMQ configurations in service properties and config classes.

Sample configuration values:

- spring.rabbitmq.port=5672
- spring.rabbitmq.username=guest

11.3 PJ USE CASES

- Send booking assigned notification to washer
- Send payment confirmation to customer

12.1 PURPOSE

12.2 FEATURES
- Create order from booking amount
- Use booking ID as receipt reference

18. PRODUCTION-READY REQUIREMENTS
The final system should be production ready and free from business logic flaws. The design must address the following:

18.1 DATA VALIDATION
- Validate every incoming DTO
- Enforce required fields on registration, booking, payment, review, and notification requests
- Validate role transitions properly
- Reject invalid status transitions
- Prevent booking on invalid or duplicate dates if required
- Ensure package activation and pricing rules are enforced

- No secret leakage in logs or response bodies
- JWT validation on every protected request
- Access control by role and ownership
- Prevent unauthorized profile edits
- Protect sensitive admin tasks from non-admin users

18.3 BUSINESS LOGIC QUALITY
- No user can see another user’s profile unless authorized
- Only customer can see their own bookings and reviews
- Washer can access only assigned bookings and own profile
- Admin can view all entities but must not modify the God account
- Payment and booking lifecycle must be consistent
- Status transitions must be validated and event-driven

18.4 ERROR HANDLING
- Global exception handlers for validation exceptions, access denied, entity not found, bad request
- Friendly user-facing messages
- Logging of exceptions without exposing internals
- Safe fallback for payment or notification failures

18.5 UX AND PERFORMANCE
- Fast dashboard loads
- Clean transitions and mobile support
- Pagination in large tables optional
- Search/filter capability on admin lists
- Loading and empty-state components
